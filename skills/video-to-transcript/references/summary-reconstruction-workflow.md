# Summary reconstruction workflow

## 模式与流程入口

写作开始前先按 `SKILL.md` 的「工作模式选择」在两种模式中二选一：**模式一 陪看**（一次一视频、转录带时间戳、支持 `seek` 回看、用户说「结束」触发收尾）；**模式二 沉浸笔记**（可多视频、转录用 `--no-timestamps`、不加载回看）。

两种模式的**最终稿契约**（保真成稿、Mermaid 触发、结构化门禁、陪看收尾三段式）见 `dense-note-authoring.md`。本文件只规定起草前的取读、分片与近乎无损的证据提取，不引入任何额外索引：陪看模式要回答「某时间点讲了什么」时，直接用 `seek` 在已落盘 `segments[]` 上二分定位即可。

## 优先级与流程

冲突时按以下顺序处理：

`用户任务 > 事实准确 > 信息完整 > Token 效率 > 文风`

取读与起草采用**保真成稿**（也是唯一流程，不再区分 economy / maximum-fidelity）。「信息完整」约束的取读即逐窗保真注记；「Token 效率」不通过主动压减信息实现，而是通过只对注记与定向回查迭代、避免二次全文通读来实现。

## 双重切片

从 `metadata.duration_seconds` 取得总时长，并估算转录文本的 Token 数：

优先使用当前模型的真实 tokenizer。运行时没有 tokenizer 时，按文本类型做保守估算并倾向多切一片，不使用过于乐观的字符换算。单片 Token 预算不得超过可用上下文的三分之一，以便给固定前缀、保真注记和模型输出留出空间；用户给出更低预算时使用更低值。

```text
时长分片数 = ceil(总时长秒数 / 3600)
Token 分片数 = ceil(预估 Token / 单片 Token 预算)
最终分片数 = max(1, 时长分片数, Token 分片数)
每片目标时长 = 总时长秒数 / 最终分片数
```

只有总时长大于 1 小时时，时长规则才产生多个片段；恰好 1 小时不因时长切片。70 分钟应得到两个约 35 分钟片段。不到 1 小时但文本过密时，Token 预算仍可产生更多片段。

这是上下文控制切片，不是主题切片。**优先按句子时间戳边界定位**，使切点落在完整句子的末尾，避免把一个完整的解释或从句切断；只有没有可用句子时间时，才按文本长度比例生硬等分。允许把切点移动到很近的句末，但不得因此让任何片段超过 1 小时或单片 Token 预算。各片不重叠并恰好覆盖原文一次。

单个句子自身已超过时长或 Token 上限时，该片只含这一个句子并允许超限 —— 宁可超限也不切断句子造成语义破裂。

转录阶段带 `--segment-plan` 时，`*.segments.plan.json` 已给出按句子边界规划好的各片起止毫秒与句子序号区间，直接采用即可；其中的 `used_sentence_boundaries` 为 `false` 时表示该次规划已降级为比例切分，此时需自己按文本比例定位。

每片复用完全相同的固定处理前缀，以便保持标准并利用可能的提示词缓存。前缀只定义角色、提取目标、紧凑格式、事实边界和禁止事项；片段编号、范围与正文作为变量放在前缀之后。

## 逐窗保真注记（每片只读一次，近乎无损）

每个片段只完整阅读一次，并按原文先后顺序生成**紧凑但近乎无损的保真注记**：只剔除口癖、口头铺垫、重复与无信息过渡；**保留一切可溯源的信息**——命名实体与代码标识符、参数/配置、数字与单位、步骤及其先后、示例与演示结果、方案取舍、条件/例外/坑与修法、讲者强调。**不对信息做「观点化」或「一句话压缩」**：观点化正是后续信息丢失的根源，保真注记以「证据在、细节在」为准。

每片产出如下结构的注记条目，条目编号全局唯一且递增：

```text
C12 ｜ 主题标签：环境准备——用 Docker 起 MySQL + Redis
- 命名实体/标识符（原样）：端口 13306；管理台 8081；脚手架「滴滴滴」
- 要点/论点：概率不落在本机，需多机共享 → 存 Redis（含讲者加的条件）
- 步骤（含次序与入参出参）：1. 同 compose 挂 mysql+redis → 2. 改端口 → …
- 数字/参数：13306（本机已占 3306 才改，无则 3306）；8081（0.0.0.0 不通用 127.0.0.1）
- 示例/演示（数量级与结果）：…
- 对比/取舍：…
- 坑/修法：…
- 教师强调/边界：端口必须与工程配置对得上
- 来源：片段2/段落18-21｜回查：否
```

注记条目包含：

- 全局唯一且递增的条目编号；
- 主题标签：该片段讲什么的概括（供合并与取用，不替代证据）；
- 上列各信息槽：命名实体、要点、步骤、数字、示例、取舍、坑、强调等，凡该片段出现的都写，保留原词与顺序；
- 片段和原文段落位置；
- `回查：是/否`。

没有内容的字段不输出。本阶段不写总结、不造过渡语，也不把独立的条件、例外、案例压缩掉；**命名或数字拿不准时，宁标「待回查」也不模糊化或臆补**。

片段完成后按编号拼接注记。只合并语义和证据都相同的重复项；重复表述带有新参数、条件、例外或案例时，保留新增信息。原始时间顺序是默认叙事顺序，只有为了读者理解必须调整时才重排，并保持步骤依赖不变。

## 按需回查

只有出现以下可观察条件时，标记 `回查：是`：

- 专有名词、数字、命令、代码、参数或版本不完整；
- 步骤依赖断裂，或跨片内容冲突；
- 案例缺少理解结论所必需的背景；
- 保真注记不足以支撑成稿所需细节，或属于低置信度提取；
- 涉及可能变化或高风险的信息，需要核对原文或权威来源。

按来源位置读取最小必要范围，通常是目标段落及相邻段落。不得重新输入完整转录，也不得因为“可能更稳妥”而回查所有注记。需要联网核实时只使用完成核对所需的一手资料，并区分讲者观点、外部事实和编辑推断。

## 总结重构（每内容单元：一轮成稿 + 一轮质检）

先按课程的自然段落把注记归并为若干**内容单元**（一个单元通常对应成稿的一个 H2），再逐单元成稿。标题和层级服从内容，不套用固定的“背景—定义—总结”模板。

单元内起草（**一轮成稿**）：从该单元的注记与定向回查结果，把事实、概念、原因、步骤、案例、边界**一次写全**，不留白、不“先写少后补密”。语气像懂行的朋友在深入浅出地解释：先让读者知道正在讨论或解决什么问题，再自然展开。合理使用 H2/H3、加粗、引用块和列表；操作流程使用有序列表。合并口语重复和无信息量过渡，但保留事实、先后关系、重要例子、限制和讲者明确表达的观点。

单元成稿后执行**一轮质检**（**QC pass**）：

1. **剔冗余**：删除车轱辘话、口头铺垫与空转过渡，合并碎片短句，抽象高维概念。
2. **补遗漏**：把该单元涉及的注记条目逐项与正文对账（起草时可临时把来源编号写成不可见标记，例如 `<!-- C12 -->`），缺事实就地补；缺证据则定向回查。
3. **守底线**：不二次全文通读、不虚构、不改讲者观点、无立场表述（底线条款见 `dense-note-authoring.md`）。

只有信息密度确实偏低或特别长的单元允许追加一轮补密；**不机械三轮重写**。单元完成后，再按 `dense-note-authoring.md` 的 **Mermaid 触发**与**结构化门禁**产出整篇终稿。合并规则（保事实、保先后、不臆造）贯穿成稿与质检全程。

不得虚构作者立场，不得虚构经历，不得虚构数据，不得虚构代码、案例、引用或执行结果。讲者观点应保持为观点；无法确认的技术细节应弱化表述或标记待核对，不能写成确定事实。

## 中文化与覆盖检查

先根据转录正文判断主要口语语言，不依赖文件名猜测。中文来源直接用自然中文起草；主要为英文或其他非中文语言时，先依照原意完成结构和事实核对，再对最终正文执行一次完整中文翻译与润色。最终只保留中文版，不另行发布原语言草稿。

中文化必须在注记编号标记仍保留时进行，并保持注记逐项可追溯，不改变因果、语气强弱、数字、单位、限定条件或讲者立场。人名、机构、产品、协议、代码、命令和 URL 不做生硬直译；读者需要时在首次出现处使用“中文名（原文）”，后文使用一致名称。翻译完成后，不允许遗留整段未说明的外语正文，但短术语、专名、代码和必要原文引语可以保留。

起草时可临时把来源注记编号写成不可见标记，例如 `<!-- C12 -->`。完成草稿后执行机械检查：

1. 每个注记至少出现一次，且没有未知编号。
2. 合并后的同一注记只覆盖一次；依赖步骤顺序正确。
3. 正文中的关键实体、数字与步骤都能对应注记或定向核对结果，而不是只有“概括对应”。
4. 非中文来源的翻译稿仍逐项覆盖全部注记，没有因翻译漏掉条件、例外或案例。
5. 删除所有注记标记后，重新检查中文表达与全文连贯性。

这项检查使用保真注记和草稿，不重新读取全文。

## 中文标题与纯净发布

完成全文后，根据实际内容拟定一个简洁、准确、可辨识的中文标题。标题优先表达核心议题或结论；不得直接复用随机媒体 ID、哈希、下载 stem 或 `source-*` 名称，也不要使用空泛的“播客总结”“视频内容整理”。来源明确给出系列名或集数时可以纳入，但不得猜测。

首行严格使用：

```markdown
# 《中文标题》
```

先清理内容标题：删除文件系统非法字符 `<>:"/\\|?*` 和控制字符，压缩多余空白，并去除结尾空格和句点；清理后为空或属于 Windows 保留设备名时重新拟题。把这个清理后的同一语义标题用于首行 `# 《语义标题》` 和文件名 `语义标题.summary.md`。

分别登记语义标题和本次实际追加的避碰序号；目标已存在时依次使用 `语义标题-2.summary.md`、`语义标题-3.summary.md`，不覆盖已有文件。数字后缀只用于文件避碰，不加入首行语义标题；一致性检查直接使用登记的语义标题和避碰序号，不通过文件名正则反推。

## 可恢复发布状态

私有暂存目录创建后立即原子写入 `.run-manifest.json`。清单持久化运行 ID、解析后的输出与暂存目录、所有运行创建文件的精确路径、清理后的语义标题、避碰序号、目标路径、暂存目录内发布候选的精确路径、候选文件的稳定实体身份（设备号与 inode，或卷与 file ID）、最终正文哈希，以及 `staging`、`draft-validated`、`publish-prepared`、`published`、`cleanup-pending`、`complete` 状态。

任何最终目录写入、发布或清理动作前都先原子更新清单。`draft-validated` 先记录尚未创建的候选精确路径、目标和正文哈希；候选只在私有暂存目录中 exclusive-create，落盘并取得实体身份后才进入 `publish-prepared`。发布后必须在删除中间产物前记录已发布或待清理状态。清单与暂存目录最后删除。

崩溃恢复只使用清单中的精确路径，并重新核对运行 ID、创建归属、目录归属、稳定文件实体身份和正文哈希。只有目标实体身份与发布前登记的临时文件身份相同，才能恢复为本次已发布；哈希只校验内容，不证明创建归属。实体不同的目标即使内容哈希相同也按名称碰撞处理。清单缺失、损坏、文件系统无法提供可靠实体身份或校验失败时停止自动发布与清理并报告，不根据文件名或通配符猜测。

标题之后直接进入正文。最终 Markdown 不包含开场寒暄、执行过程、切片说明、注记清单、内部编号、时间戳、日志、质量评分或总结性废话。

草稿、原语言稿、翻译稿、注记材料和发布候选始终写入私有暂存目录。确认正文非空、标题和文件名合规、中文化完成、注记覆盖完成、内部标记清零后，先持久化 `draft-validated` 状态、尚未创建的候选精确路径、目标和正文哈希；再在暂存目录 exclusive-create 候选，写入、落盘并读取稳定文件实体身份，最后持久化实体身份与 `publish-prepared`。候选创建前后的崩溃都不会在最终目录留下未登记临时文件。

暂存目录位于输出目录内，候选和目标因此处于同一文件系统。使用保留实体身份、目标存在即失败的原子 `no-clobber` 操作发布，例如硬链接。硬链接方案在 `published` 状态持久化前保留暂存候选链接，之后把候选作为登记的暂存中间产物清理。不得使用会覆盖目标的 `replace` 语义；发生并发占用时，无论内容是否相同都登记下一个避碰序号并重试。无法获得可靠实体身份或身份保持的 no-clobber 原语时停止发布并报告。

成功发布之后才清理本次运行的私有暂存目录；最终总结之外不保留切片、注记、转录文件、ASR 响应、原语言草稿、翻译草稿或发布候选。发布失败时保留暂存目录；既有文件和用户输入永不删除。

最终总结发布后若暂存清理失败，不回滚或删除总结，也不把任务标记为完整成功。保留并报告尚存的本次运行精确路径；后续重试仍需逐项验证创建归属和私有暂存目录归属。所有残留中间产物与空暂存目录清除后，唯一总结交付才完成。
