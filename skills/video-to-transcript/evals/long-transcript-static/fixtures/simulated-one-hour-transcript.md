# 模拟一小时课程转写：长文档整理与安全发布

> 这是为静态评估编写的长转写夹具，不是真实录音转写，也不代表执行过模型。

P01 这节课讨论一个常见但容易被低估的问题：当课程转写很长时，整理者如果从头到尾只写一份摘要，前面出现的定义、后面补充的条件以及中间的操作步骤很容易失去联系。短文本里可以依靠工作记忆保持上下文，长文本里却需要显式记录当前主题、已经完成的步骤、尚未解释的术语和待核对的问题。我们把这些信息叫作主题状态，它不是原文的替代品，只是让相邻文本块能够衔接。整理者仍然必须回到原始段落确认每个重要结论，尤其是命令、参数、产品行为和讲者声称的结果。为了让演练可复现，后面会给每个独立事实一个固定标识，但最终技术文档不会把这些内部标识当成正文内容。课程还会故意把一个流程分布在两个文本块中，用来检查合并之后的先后顺序是否仍然正确。

P02 先从读者问题开始。读者拿到连续转写后，通常想尽快得到一篇能直接阅读的技术文档，于是最直觉的做法是边读边改写。这个做法在主题少、段落短时可以工作，一旦文本超过单次整理的稳妥范围，边读边写就会产生三个风险。第一，后文对前文概念的修正可能无法回填；第二，跨段的步骤会被分别概括，依赖关系消失；第三，相同概念在多个位置出现时，整理者可能重复写入，而只出现一次的限制条件反而容易遗漏。更稳妥的方式是先切分自然语义单元，再提取事实卡，然后按主题合并并回查来源。切分不能按固定字符数生硬截断，因为句子、代码块、命令和连续操作都可能横跨机械切点。自然边界优先于追求完全相等的块长。

P03 [F01] 讲者把校验门定义为：只有草稿非空且所有必填段落都存在时，发布动作才可以继续。这里的重点不是给检查动作取一个新名字，而是明确发布前存在一个不可跳过的条件。校验门接收草稿和结构要求，输出是否允许继续。它不负责创造缺失事实，也不替整理者决定冲突内容。如果草稿缺少限制段落，正确行为是回到事实卡和来源检查，而不是自动补写一个听起来合理的风险。如果草稿为空，发布器应停止，不创建最终文件。这样的定义把文档整理和文件发布分开：前者处理事实与结构，后者只在结果满足条件时执行可控的文件操作。后面的演练会让空草稿通过一次失败路径，用来说明失败不会波及原始转写产物。

P04 事实卡是一种中间记录。每张卡至少写明来源文本块、原文段落、事实类别、原句或足够精确的摘录，以及准备在合并文档中表达的内容。事实类别不能只写一个宽泛的“知识点”，因为定义、关系、步骤、依赖、讲者观点、适用条件和风险在最终文档中的处理方式不同。定义需要保留原意；关系需要说明组件如何协作；步骤需要保持顺序；观点要标明是讲者判断；条件与风险不能被宣传式表达吞掉。事实卡阶段不追求成文，也不因为内容重复就立即删除。只有在跨块合并时，整理者才能看见哪些卡真正重复、哪些卡只是描述同一主题下的独立参数或例外。删除独立条件会造成遗漏，保留同义重复又会让读者误以为它们是两个不同结论。

P05 [F02] 规范化文本提供事实内容，事实卡保存来源关系，发布器只消费已经回查的合并结果。三者的关系形成一条单向链路。规范化文本是主要事实来源，不能在文档失败时被覆盖；事实卡把来源和类别结构化，便于跨块比较；合并结果经过回查后才交给发布器。发布器不读取原始音频，也不自行推断缺失内容，因为它的职责是选择未占用路径、写入临时文件、校验非空并完成替换。若把发布器放在事实回查之前，文件可能已经落盘，之后发现错误只能再生成新版本。若让事实卡脱离原文，来源定位就失去意义。保持职责边界可以把失败限制在当前阶段，并让重试从已保存的转写开始，而不是重新下载和转写媒体。

P06 接下来说明分块。夹具选择段落、主题转折和完整步骤作为候选边界。每块目标长度受两个上限约束：通常希望落在六千到八千字符之间，但当可用上下文的三分之一更小时，应采用更小的上限。这样做不是为了制造绝对安全数字，而是为后续事实卡、合并草稿和回查保留上下文空间。切分器沿候选边界向前寻找，不在句子中间切开，也不把围栏代码块拆成两半。若一个连续操作的说明略微超过目标，宁可移动边界，也不把“创建临时文件”和“校验后替换”分到彼此没有主题状态连接的块里。固定重叠会复制原文，从源头增加重复风险，所以这里用主题状态传递衔接信息，不复制上一块末尾的正文。

P07 [S1] 第一步，读取规范化文本并建立带来源段落的事实卡。这一步只做提取和分类，不开始写最终文章。整理者逐段识别读者问题、旧方式不足、原文定义、组件关系、操作步骤、先后依赖、代码命令参数、讲者描述的结果、实例、适用条件、限制风险、讲者观点和待核对事项。每条记录带上文本块编号与原文段落编号。遇到版本敏感的产品行为时，卡片先标为待核对，只有查到官方一手资料后才能改成已验证事实。找不到资料并不意味着可以省略原始说法；如果它对理解必要，就以不确定状态保留。该步骤完成后，主题状态写明当前流程已经建立事实卡，下一块需要继续处理依赖合并与发布。

P08 [F03] 只有目标文件尚不存在且临时草稿通过校验时，原子替换才适用于这次发布。这里有两个同时成立的条件。目标文件不存在，保证这次操作不会覆盖用户已有文档；临时草稿通过校验，保证替换的输入至少非空且包含必需结构。如果目标名已经占用，发布器先选择带数字后缀的新路径，而不是把旧文件当作替换目标。如果草稿没有通过校验，临时文件可以保留用于排查，但最终路径不能出现一个半成品。所谓原子替换只描述同目录临时文件到选定最终路径的发布动作，它不能证明正文事实正确，也不能替代前面的来源回查。文件系统语义和内容质量是两个不同边界，课程要求两者都明确。

P09 下面的代码只是静态夹具中的口述示例，用于检查围栏是否被分块器拆开。它表达的动作是写入同目录临时文件，确认草稿非空，然后把临时文件替换到已经选好的未占用目标。这里没有执行记录，所以最终文档若引用它，只能说预期行为，不能声称已经观察到成功。

```python
temporary.write_text(draft, encoding="utf-8")
if not draft.strip():
    raise ValueError("empty draft")
temporary.replace(chosen_target)
```

代码中的 `draft.strip()` 用于拒绝只包含空白的草稿，`chosen_target` 必须在写入前完成冲突检查。代码块从开围栏到闭围栏属于一个完整语义单元，任何块边界都只能出现在闭围栏之后。围栏后的解释同样重要，因为读者需要知道参数、预期结果和实际意义。这个示例没有包含异常恢复、权限错误或跨文件系统移动，因此不能被扩写成完整的生产发布器。第一块到这里结束，主题状态记录 S1 已完成、S2 待执行，并保留“失败草稿如何处理”这一未闭合问题。

P09A 在第一块结束前，再检查一次术语边界。课程里可能把“原子写入”“原子替换”和“安全发布”混在一起说，整理时不能因为它们听起来相近就当成同一个动作。写入临时文件只是准备数据，替换是文件系统动作，安全发布还包含冲突检查、非空校验和失败保留。事实卡要保存讲者原来的定义，再在合并阶段说明这些术语之间的关系。若官方文档只支持其中一部分语义，就把支持范围写清楚，不把平台特定保证扩展到所有文件系统。术语精确性优先于句式整齐，必要时可以保留较长解释。

P09B 参数也需要独立记录。一个命令可能在第一段介绍工具名，在后面的问答里才补充参数条件。如果切块后只保留第一处摘要，参数就会遗漏；如果把两处完整句子都复制进最终文档，又可能产生重复。事实卡应分别记录工具、参数、条件和讲者描述的结果，并通过来源位置建立关联。合并时先判断它们是同一事实的重复表述，还是同一主题下互补的信息。只有同义重复可以折叠，新增条件、异常和版本边界必须留下。

P09C 讲者观点与可验证事实也要分开。讲者可能说某个工具“最好用”或某项技能“必须掌握”，这类评价可以作为教学观点保留，却不能改写成行业共识。产品版本、命令参数和公开行为如果会变化，应查官方一手资料；无法联网或用户禁止检索时，文档说明验证范围，并把必要但未确认的内容标记为待核对。事实卡中的类别让合并器知道哪些句子需要观点归属，哪些句子需要外部核验，哪些句子只需忠实保留原意。

P09D 代码和命令之后必须有解释，但解释不能凭空增加执行结果。静态夹具里的代码从未运行，所以只能说明每行意图和预期结果。若真实工作流执行过命令，证据应包括命令、输入、退出码和相关输出，文档才可以使用“观察到”或“实际结果”。讲者在视频里声称运行成功，属于讲者描述的结果；整理者自己运行成功，才属于当前执行证据。把两者混淆会让读者误判验证强度。

P09E 第一块的最后一次检查确认没有未闭合围栏、没有半句被切开、没有把 S1 的动作拆散。块末主题状态只记录衔接所需信息，不复制 P09A 到 P09D 的正文。这样第二块知道当前主题是来源回查与发布、当前步骤是 S1 完成、S2 待执行，同时仍需从事实卡和原文定位获取细节。若主题状态包含新的技术结论而原文没有对应卡片，它就越过了自身边界，评估应视为不合格。

P10 第二块从主题状态继续，而不是重复第一块末尾的正文。此时已经有带来源位置的事实卡，下一步要按主题合并。合并不是按 B01、B02 的顺序把摘要首尾相接，而是把定义放到定义位置，把组件关系放到组成位置，把步骤按依赖重新连接，把限制放到限制位置。相同事实的同义表达只保留一次，独立参数、条件和例外全部保留。若两块对同一版本行为给出不同说法，合并结果同时保留并标为待核对，不能由整理者凭印象裁决。跨块流程尤其需要检查依赖字段，因为一个步骤可能出现在第一块，后续动作在第二块；主题状态只能提醒当前进度，真正的顺序依据仍然来自事实卡和原文。

P11 为了检查覆盖范围，评估器从夹具开头按边界标记生成两个连续切片，再把切片直接连接并与原始夹具逐字符比较。如果完全相同，说明没有因切分引入重叠或缺口。这个检查只证明静态产物的源覆盖，不等于自然语言理解已经正确。每个文本块还必须包含主题状态和至少一张事实卡，否则不能说它遵循了块、状态、卡片、合并的工作流。事实卡中的原句必须在指定块恰好出现一次，合并表达必须在最终文档恰好出现一次。通过计数可以发现预先指定的独立事实是否重复或遗漏。对于没有列入唯一事实清单的普通背景句，评估器不做语义质量判断，因此报告必须诚实地限定证据范围。

P12 跨块步骤的检查采用显式依赖。第一步没有前置步骤，第二步依赖第一步，第三步依赖第二步。评估器确认源句位于声明的文本块，确认这些步骤至少横跨两个块，再确认最终文档中的表达只出现一次并按照索引递增。若第二步出现在第一步之前，即使三句话都存在，也会判定顺序失败。若第三步没有依赖第二步，连接检查会失败。这个方法不会评判步骤写得是否优美，它只针对绑定设计要求的“不断裂、保持原始操作顺序”。把可机械验证的关系写成数据，可以让评估在没有第三方包、没有网络和没有模型调用时复现，也避免把人工印象包装成行为测量。

P13 [F04] 讲者描述的演练结果是：故意制造空草稿后，发布器拒绝创建最终文件，并保留原始转写。这里必须保留“讲者描述”这个归属，因为静态夹具没有真正执行发布器。最终技术文档可以陈述讲者在课程中如何描述演练，但不能把它改写成当前评估器已经观察到的系统结果。若未来加入真实执行测试，报告可以另行记录命令、退出码和文件状态，再使用“观察到”一词。现在的证据只来自固定源句、事实卡和合并输出之间的对应关系。原始转写保留是失败边界的一部分：技术文档整理失败不能删除、覆盖或改写已经成功生成的 transcript Markdown、规范化 JSON 与原始 ASR JSON。

P14 [S2] 第二步，在第一步事实卡完成后，按依赖关系合并跨块步骤。这一步读取两块事实卡，先把重复定义折叠，再把独立条件和例外保留，随后根据 `depends_on` 字段连接步骤。合并器不能只按块编号排序，因为主题可能在后文回到前面的问题；它要按读者理解顺序组织背景、定义、组成、过程、实例、限制和总结。对步骤而言，依赖关系高于原始卡片列表位置，但不能反转原文明确的操作顺序。完成合并后，每个重要结论、参数、命令和代码都要回查到文本块编号与原文段落编号。无法定位的内容从草稿移除或标为待核对，不能为了让文章完整而补写。

P15 [F05] 合并必须先完成来源回查，再执行非覆盖发布；两个动作不能交换顺序。这个依赖保护了事实优先级。如果先发布再回查，错误内容可能已经成为用户看到的正式文件；即使之后生成带后缀的新版本，旧错误文件仍然存在。来源回查确认重要内容能够落到原文段落或官方一手资料，非覆盖发布则确认选定路径没有占用并使用同目录临时文件。两者分别处理内容可信度和文件安全。合并结束并不自动代表可以发布，只有校验门通过后，发布动作才继续。若回查发现冲突，文档保留两种说法并标为待核对，发布器不参与裁决。

P16 事实去重与事实遗漏使用同一组固定标识检查。清单中的每个事实标识必须对应一张事实卡，不能出现两张同标识卡，也不能缺卡。每张卡的源句在夹具中恰好出现一次，合并表达在输出中也恰好出现一次。如果源句出现两次，说明夹具本身无法区分来源；如果合并表达出现两次，说明重复没有消除；如果一次也没有，说明事实被遗漏。这个办法对指定事实提供确定证据，但不声称覆盖所有自然语言含义。评估报告会给出卡片数量、步骤数量、块长度和每个不变量的布尔值。测试套件读取机器可读 JSON，并逐项断言，而不是只检查脚本是否能启动。

P17 [S3] 第三步，在第二步合并并回查完成后，选择未占用文件名进行原子发布。发布器从规范化转写的基名派生技术文档名称，若目标存在就依次尝试数字后缀。选定路径后，完整草稿先写入同目录临时文件，校验非空和必填结构，再替换到最终路径。任何文档阶段失败都报告部分成功，保留三种转写产物，并保留可用于重试的草稿。清理媒体仍由转写 CLI 的删除门控制，文档整理不得扩大删除范围。这个步骤依赖 S2，是因为只有合并和来源回查完成的草稿才有资格进入发布校验。

P18 [F06] 静态演练只能证明这些固定产物满足约束，不能证明任何模型在开放输入上的生成质量。这个限制必须在 README、证据清单和机器报告中保持一致。评估没有调用第二个大语言模型，没有访问网络，也没有运行云转写。它验证的是一个超过八千字符的模拟夹具如何被两个有主题状态的块覆盖，围栏代码是否完整，事实卡是否带来源，跨块步骤是否按依赖连接，以及指定独立事实是否在合并后恰好出现一次。这样的静态评估适合作为回归保护和工作流示例，不适合作为模型能力分数。未来若真的运行模型，应把提示、模型、输入、原始输出和评分方法另行保存，并明确区分模型行为证据与本次静态产物证据。

P18A 最终文档的结构检查同样不能替代事实检查。背景、定义、组成、过程、实例、限制和总结都存在，只能证明读者理解顺序有基本框架；每一节仍可能包含无来源结论。评估因此把结构视为输出形态，把事实唯一性、步骤依赖和来源覆盖视为独立不变量。一个检查通过不能掩盖另一个检查失败。报告逐项输出布尔值，测试也逐项断言，方便定位是围栏切分、卡片缺失、步骤断裂还是合并重复。

P18B 对失败路径的描述要保持边界。转写失败时，CLI 根据既有删除门保留本次运行产生的媒体；转写成功而文档整理失败时，三种转写产物保持不变，文档草稿可供重试。静态评估只检查合并输出和证据文件，不触发媒体清理，也不修改 transcript 文件。把这些职责写清楚，可以防止未来维护者为了“清理干净”而在文档阶段扩大删除范围。安全规则不依赖文风，也不能因为用户希望简短回答就被省略。

P18C 非覆盖命名也需要在多次运行中保持可预测。第一次目标使用基名，已存在时选择 `-2`，之后依次选择更大的可用数字。选择过程只能查看候选是否存在，不能先删除旧目标再占用原名。临时文件与最终文件位于同一目录，使替换语义更明确；如果平台或文件系统不保证预期行为，文档应说明限制。静态输出没有实际创建这些候选文件，因此它只描述工作流合同，不声称碰撞演练已经运行。

P18D Humanizer 式编辑只能在事实和技术完整性之后进行。它可以删掉空泛开场、虚假权威、无支持数字、机械连接词、重复副词和宣传形容词，却不能添加第一人称经历、情绪、作者立场、代码、引用或例子。它也不能为了避免规则化外观而删除必要列表、标题、冒号或三项结构。评估输出刻意保持直接说明，因为这里的目标是呈现可检查关系，不是模拟个人写作风格。风格冲突时，事实与技术边界始终优先。

P18E 课程到这里收束。长文本整理的关键不是把每块分别总结，而是让自然边界、主题状态、事实卡、依赖合并、来源回查和安全发布形成连续流程。静态夹具通过固定输入与固定输出提供可复现回归证据，同时明确不冒充模型行为评估。维护者可以修改夹具中的某个不变量来验证测试是否会失败，例如复制一个合并事实、删除步骤依赖或把块边界移进代码围栏。验证完失败后应恢复固定证据，再运行标准库评估和完整单元测试。

P18F 还要注意字符阈值只是保守路由条件，不代表真实一小时课程必然具有固定字数。语速、停顿、代码演示和互动都会改变转写长度。这个夹具用“模拟一小时”表达场景复杂度，用超过八千字符触发绑定的长文本路线，并不声称字符数与时长存在精确换算。评估报告只陈述实际读取到的字符数。若未来换成真实一小时转写，应保留真实来源说明，并重新检查块长、自然边界与上下文预算，而不是沿用夹具的块位置。

P18G 可移植性要求所有路径从评估脚本自身位置推导。脚本只使用 Python 标准库读取 UTF-8 文本、JSON 证据和 Markdown 输出，不依赖当前用户下载目录、ZIP 包、站点包或网络。测试通过 `python -B -S` 等价环境运行评估器，`-B` 防止生成字节码，`-S` 避免加载 site-packages。这样一台只具备兼容 Python 的机器也能复现不变量检查。可移植并不表示跨平台文件系统发布语义已经实测；那仍属于本静态评估之外的边界。

P18H 最后区分“证据存在”和“证据充分”。块切片、事实卡和合并文档让审阅者看见工作流各阶段的固定产物，自动断言则确保关键关系不会静默退化。这些证据足以支持本次回归目标：围栏未拆分、步骤有连接、指定事实无重复遗漏。它们不足以回答文章是否自然、所有事实是否都被人类正确识别、模型面对陌生主题是否稳定。报告必须同时呈现通过项和限制，避免把局部机械验证扩大成整体质量背书。

P18I 评估完成后，维护者应把机器报告与固定产物一起阅读。字符数和块数说明路由确实进入长文本场景，块长度上限说明较小上下文预算得到尊重，卡片与步骤计数说明证据规模，五项不变量说明具体约束。任何一项为假时脚本返回非零退出码，单元测试展示失败项名称。修复应针对对应产物或合同，不应通过删除断言来制造通过。保持这种可诊断性，才能让静态评估长期承担回归保护作用。审阅者还可以直接打开证据 JSON，核对每张卡的字段、来源段落和合并表达，确认自动报告没有隐藏输入假设。每次修改证据后都要重新运行完整检查，不能沿用旧报告。
