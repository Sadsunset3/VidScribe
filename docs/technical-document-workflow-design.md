# 技术文档整理工作流设计

## 目标

本文说明 VidScribe 如何把音视频转写结果整理为可直接阅读、可追溯的技术文档。转写程序负责确定性的媒体处理、语音识别、结果保存和安全清理；文档整理阶段在转写成功后读取规范化文本，提取事实、组织结构并发布最终文档。

最终新增同源的 `*.technical.md` 文件。现有 `*.transcript.md`、`*.transcript.json` 和 `*.asr.raw.json` 继续保留，作为追溯事实、排查识别错误和重新整理文档的依据。

## 优先级

所有冲突按照以下顺序处理：

1. 用户任务
2. 事实准确
3. 技术完整性
4. 风格约束

这意味着风格规则不得驱动内容补写、事实改写、代码猜测或技术边界删除。

## 架构边界

### CLI 负责的工作

- 接收 URL、本地视频或本地音频。
- 下载最佳音频优先的单条媒体。
- 检查媒体并在需要时分离或规范化音频。
- 调用 Paraformer-v2 生成无时间戳转写。
- 原子保存三种转写产物。
- 在输出验证成功后清理本次运行创建的媒体。

CLI 不调用额外的大语言模型，也不承担技术文章生成。这样可以避免新增模型配置、费用、上下文长度和供应商兼容问题。

### 文档整理阶段负责的工作

- 确认三种转写产物有效。
- 读取规范化 JSON 的 `text` 与 `metadata`。
- 根据事实边界整理技术内容。
- 生成并保存 `*.technical.md`。
- 对最终文档执行结构、术语、代码、边界和风格检查。
- 向用户优先返回技术文档路径，同时提供转写与审计文件路径。

如果转写成功但技术文档整理失败，工作流报告“转写成功、文档整理失败”的部分成功状态，并保留全部转写产物供重试。

## 事实处理

转写文本是主要事实来源，但语音识别结果可能包含专有名词、参数、版本号和代码误识别。整理时采用以下规则：

1. 从转写中提取明确陈述，不改变原意。
2. 区分事实、讲者观点和整理者推断。
3. 技术名词、版本、API、参数或命令存在疑点时，优先查阅官方一手资料。
4. 无法验证但必须保留的信息标记为“待核对”。
5. 不为追求完整而虚构例子、数字、作者经历、代码或引用。
6. 口述代码只有在语义明确时才整理成代码块；否则保留文字说明并标记待核对。

联网不可用或用户禁止检索时，文档明确说明验证范围，不把未验证内容写成确定事实。

## 文档结构

技术文档按照读者的理解顺序组织：

1. 背景：先描述读者遇到的问题，以及旧方式为什么不够。
2. 定义：用一句白话解释新概念，再给出正式术语、英文名称和缩写。
3. 组成：说明关键模块、角色或概念之间的关系。
4. 过程：复杂流程使用编号步骤，每一步只完成一个动作。
5. 实例：使用转写或可靠资料中真实存在的例子、代码和命令。
6. 限制：为重要结论说明适用条件、缺点、风险或版本约束。
7. 总结：重新收束核心理解，并给出一个可继续尝试的方向。

代码或命令之后立即解释关键参数、预期结果和实际意义。不能确认执行结果时使用“预期结果”，不得伪装成已经验证。

## 表达规则

- 以清晰陈述句为主。关键判断可以短，原因解释可以稍长。
- 使用“也就是说、这意味着、举例来说、注意、因此”等连接语标明逻辑关系，但不机械重复。
- 语气平等、耐心、直接，不使用论文腔，也不过度娱乐化。
- 专业概念首次出现时先白话解释，再补正式名称、英文和缩写。
- 删除空泛形容、宣传语言、虚假权威、机械总结和无信息量的修辞。

## 内容质量边界

语言优化只能提高可读性，不能改变事实、技术含义或证据强度。整理过程遵守以下原则：

- 最小修改，保留原意。
- 删除“值得注意的是”“随着技术发展”等没有信息的套话。
- 检查“不是 A 而是 B”是否制造假靶子、同义替换或无关转折。
- 删除未经验证的机构、报告、数字和引用。
- 使用具体工具名、参数、动作和结果，避免空泛表达。
- 调整连续同构句、重复副词和过度整齐的段落。

以下做法不得用于技术文档整理：

- 强制加入第一人称、情绪、作者立场、轶事或自嘲。
- 为增加“活人感”而虚构细节、数据或经历。
- 强制使用网络口语、口头禅、粗俗表达或故意打断逻辑。
- 全面禁用冒号、破折号、引号、列表或小标题。
- 为避免三项列表而删除必要技术内容。
- 用极端数字替换原始数字以增强冲击力。
- 输出 AI 味等级、修改统计或 L1-L4 报告。

## 输出命名与覆盖策略

技术文档沿用规范化转写文件的基名：

```text
source-id.transcript.json
source-id.technical.md
```

如果目标文件已经存在，使用 `-2`、`-3` 等后缀，避免覆盖用户已有文档。生成过程先写临时文件，再执行同目录原子替换。

## 长文本处理

转写阶段不切割音频或文本。CLI 将完整音频交给 Paraformer，并把返回内容保存为一个连续的 `text` 字段。长文本只在技术文档整理阶段切分，这样不会改变 ASR 的上下文，也不会引入音频切点造成的漏字。

当转写超过约 8000 个中文字符，或已经占用当前模型可用上下文的约三分之一时，启用分块整理。字符阈值是保守默认值；模型上下文更小时，以可用上下文比例为准。

### 自然边界切分

1. 先识别空行、完整句子、主题转折和章节切换。
2. 每块目标长度为 6000～8000 个中文字符。
3. 不在句子、代码块、命令或连续操作步骤中间截断。
4. 如果自然边界接近目标长度，移动切点到边界，不为满足固定长度破坏语义。
5. 不机械复制固定长度的重叠文本，避免后续文档重复。

每块携带上一块的“主题状态”，包括当前主题、流程进行到的步骤、尚未解释的术语和未闭合问题。主题状态只提供衔接信息，不替代原始文本。

### 事实卡提取

每个文本块独立生成结构化事实卡，字段包括：

- 读者问题和旧方式不足
- 专业概念及原文定义
- 组成部分和相互关系
- 操作步骤及先后依赖
- 代码、命令、参数和讲者描述的结果
- 实例
- 适用条件、限制和风险
- 讲者观点
- 待核对内容
- 来源块编号和原文段落编号

事实卡阶段只提取和分类，不写最终文章，不为了简洁删除技术细节。

### 跨块合并

1. 按主题合并事实卡，而不是按原始块顺序简单拼接摘要。
2. 合并重复概念，保留所有独立参数、条件和例外。
3. 跨块步骤按照依赖关系重新连接，保持原始操作顺序。
4. 来源发生冲突时保留两种说法并标记待核对，不擅自裁决。
5. 按固定文档结构生成完整草稿。
6. 将每个重要结论、参数、命令和代码回查到来源块与原文段落。

分块中间结果不作为最终文档交付，除非用户明确要求。

由于最终文档不显示时间戳，内部来源定位使用“文本块编号 + 原文段落编号”。如果用户需要跳回视频位置，可以重新启用仅供元数据使用的时间戳，但不得把时间戳加入最终技术文档正文。

## 生成后检查

- 是否先建立问题再讲概念？
- 是否存在没有解释的术语或代码？
- 是否按照读者理解顺序推进？
- 是否只有优点而没有边界？
- 是否为了模仿而堆叠口头禅？
- 是否出现脱离事实依据的作者立场？
- 是否把讲者观点误写为公认事实？
- 是否对命令结果作了未经执行的成功声明？

检查用于修订正文，不单独写入最终技术文档。

## 验收策略

### 工作流契约

- 有效转写能够继续生成 `*.technical.md`。
- 事实优先级和七段理解顺序保持稳定。
- 表达优化不能绕过事实与技术边界。
- 输出命名不覆盖已有文件。
- 文档整理失败不会删除或覆盖转写产物。

### 内容质量

使用包含术语、步骤、代码、命令和限制条件的代表性转写进行验收，验证：

- 无时间戳。
- 开头先建立问题。
- 首次出现的专业术语有白话解释和正式名称。
- 流程步骤一次只做一件事。
- 没有转写或官方资料无法支撑的事实。
- 至少说明一个适用边界或风险。
- 结尾包含核心收束和可继续尝试的方向。
- 长文本经过分块和合并后，代码块保持完整，跨块步骤保持连续，独立事实没有重复或遗漏。

### 失败边界

- 缺少有效转写文本时不创建技术文档。
- 目标文件已存在时不覆盖。
- 无法验证的代码、版本或参数不会被写成确定事实。
